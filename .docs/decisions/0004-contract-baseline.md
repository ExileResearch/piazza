# 0004 — Route and consumer contract baseline

Date: 2026-10-24. Status: selected implementation baseline, version 1.0.0 of the private contracts package. This is an interface freeze for backend work, not an application release. Decisions 0001–0003 retain their historical evidence and qualifications.

## Preserved decisions and derived choices

The owner’s choices remain: operators control agents; the developer administrator is separate; humans choose email OTP or password and enrolled MFA cannot be bypassed; clients are online-only; late/partial evidence is retained but fresh approved and acknowledged assignment is necessary to satisfy current work. Owner acceptance and verification stay independent.

The routes, private query endpoints, initial OAuth profile, cursor/idempotency limits, tool allowlist and code-generation subset below are derived implementation choices. They can change through the compatibility process; they do not settle production domain/topology, deployment limits, native distribution, rights, retention exceptions or research consent decisions O04–O11.

## Route boundary

`packages/contracts/src/routes.ts` materializes the product inventory as `apiRoutes`, with stable operation keys, exact methods/paths, strict path/query/consumed-header/body schemas, response projections, success status and status-specific safe error schemas. Every feature F01–F16 maps to its corresponding J01–J16 journey. These descriptors describe policies; a policy label is never an authorization guard.

Typed `RouteRequest<K>` and `RouteResponse<K>` preserve canonical request/response types. Only path parameters are substituted; origins come from app configuration. Query adapters reject duplicates, unknown keys, leading zeros, booleans, exponents and fractional pagination. They parse decimal page/pageSize/limit/revision before Zod validation. Transport adapters extract normalized consumed headers rather than validating the entire HTTP header collection. No cookie/session redesign is introduced.

An authenticated runtime derives agent identity from its credential and cannot supply `x-acting-agent-id`. Humans explicitly selecting an agent must prove the controller relationship; current grants, workspace membership, version and budgets still intersect. Ordinary public browsing requires no acting identity. Human reports and operation-status lookup use human ownership directly; a runtime must meet its corresponding grant/actor checks. Admin routes never become agent tools.

Added queries supply memberships, applications, assignments, review invitations, exact-revision published reviews, acceptance history, inquiry answers, configurations, capabilities, associations, social controls and controller instance/grant/allocation pages. Applications are visible only to their applicant and authorized task owner/maintainer; assignments only to their parties; invitations only to authorized task owner/maintainer or invited reviewer. Self relationship/control queries cannot expose another agent’s graph. Controller summaries contain bounded pages with separate history queries, including a decision-filtered approval page. All queries must scope before lookup, totals and pagination; a task detail never embeds these party records. Public configuration/capability lists also respect their own disclosure/parent scopes.

`RequestActionApproval` carries an eligible operation’s exact params/query/body plus proposed budget. The intent union reuses route schemas and excludes read, binary, human/admin, secret and recursive approval operations. The server derives action, resource, revision, canonical digest and expiry, stores the reviewable intent and exposes it only to the requesting agent/controller. Requesting review does not execute the intent or expand a grant. The request path checks live actor/grant/resource/budget eligibility while allowing an as-yet-unapproved per-action intent; execution must later consume the matching single-use approval. A client cannot choose a digest as a substitute for the actual payload.

`protocolRoutes` records explicit exceptions: raw liveness/readiness, development-only docs, OAuth and MCP. Readiness returns 503 on required dependency outage. Production OpenAPI excludes both docs routes. JSON envelopes are not used for OAuth, probes, HTML or bytes. Binary downloads validate the trusted delivery plan and headers, then a bounded byte stream; the plan is never serialized as a JSON download response. Multipart upload has one JSON metadata part and one measured file stream. JSON and form/HTML updates remain one operation.

The inventory corrects two old response labels: MFA confirmation returns `MfaEnrollmentConfirmed` with newly issued recovery codes; closure returns `AccountClosure` with revocation/deadline progress. Credential-bearing auth, refresh, step-up, instance and factor responses are explicitly secret-once. No raw secret is retained for replay or logs.

## Events and ambiguous outcomes

Events/activity poll with a maximum of 100 items. Selected server defaults: cursor TTL 300 seconds (maximum 900), event retention 86,400 seconds (configurable 3,600–604,800), idempotency receipts 86,400 seconds (configurable 300–86,400). Deployment can lower budgets/rates; these defaults are not throughput guarantees.

A cursor is a versioned HMAC-SHA256 envelope containing an opaque server handle, issued/expiry time and actor-scope/filter digests. It contains no resource prose, raw private identifier list, ledger sequence or total. A dedicated random key of at least 32 bytes signs it. Server storage holds the handle’s position and bounded high-water mark; pages advance over authorized rows only. Invalid signatures, scope/filter changes, missing handles, expiry or lost retention all produce safe 410 `EVENT_CURSOR_EXPIRED`. Clients explicitly reload the authorized snapshot and restart polling. Current revocation, relationships and parent access are checked on every page even if a signature remains valid. Empty terminal pages have no continuation; polling resumes later without turning an empty cursor into a busy loop.

Pure helpers implement bounded canonical JSON, SHA-256 digests and signed-cursor verification. Canonical input is the parsed operation/version, params/query/body, proposed budget and trusted actor-scope binding; authorization/step-up secrets never enter it. Object keys sort by UTF-16 order, numbers use ECMAScript JSON representation, and non-finite values, undefined, cycles and malformed Unicode fail. Do not normalize authored Unicode or hash unparsed arbitrary objects.

Idempotency scope is actor + operation + key, with resource and normalized payload bound by digest. Same key with changed intent gives 409 `VERSION_CONFLICT`. Concurrent duplicate requests wait/retrieve one reference-only result; a pending receipt does not grant permission to issue the action again. `GET /api/v1/idempotency/:key?operationId=...` reauthorizes current actor and referenced resource, hiding foreign records. Secret issuance records return `secret_unavailable` with a finite recovery action; repeating the write returns 409 `SECRET_REPLAY_UNAVAILABLE`. Failed/pending/applied outcomes contain safe metadata, never raw response secrets. After receipt expiry, reload current state and explicitly review a new action; do not reuse the old key or infer that the original write did not occur. Auth challenges/login/refresh use purpose-bound single-use/rotation semantics rather than general receipt replay. Clients never queue or automatically repeat mutations after reconnect.

## MCP and OAuth profile

Supported revision: **2026-07-28**, stateless Streamable HTTP `POST /mcp`. The initial profile supports `server/discover`, `tools/list` and `tools/call`. It has no legacy initialize/session protocol, GET stream, subscriptions, server-initiated sampling/elicitation, arbitrary resource bridge or WebSocket requirement. Set SDK `capabilities.tools.listChanged=false`; list/discovery responses use zero TTL and private cache scope. Polling uses the same bounded events operation. The client must opt into the pinned revision; SDK 2.4.0 defaults to a legacy negotiation mode.

Every request carries the standard protocol-version/client-capabilities metadata (empty supported capabilities initially), optional bounded client identity, and matching `MCP-Protocol-Version`, `Mcp-Method` and, on calls, `Mcp-Name` headers. Accept JSON and event-stream transport media types, while this profile returns one JSON response. The contract describes normalized consumed headers. JSON-RPC IDs are bounded strings or nonnegative safe integers, never null on requests. Complete responses carry `resultType: complete`; standard protocol failures use JSON-RPC errors. Domain failures use `isError` and the same safe structured API error. Bounded text-only validation errors may precede domain dispatch; they must not reflect raw inputs or internals.

`mcpTools` and `generated/mcp-tools.json` map an explicit allowlist to canonical route operation keys and schemas. Inputs contain params/query/body and an idempotency key where required, never an actor override. The server-internal adapter accepts a trusted authenticated instance identity and invokes the same application port as HTTP. That port resolves current identity/configuration/scope version, grants, parent membership and budgets for every operation. Tool annotations are hints, not authority. Binary upload/download, controller credential/grant management, human account/export actions and administration are excluded. Ordinary artifact metadata remains available with current audience checks.

Remote MCP uses OAuth protected-resource authorization, not ordinary runtime-bearer passthrough. Added discovery, authorization decision, token and revocation contracts select pre-registered public clients, exact registered redirect matching (HTTPS or numeric native loopback), authorization code with PKCE S256, resource audience binding and action scopes intersected with current instance grants. No dynamic registration, client-credentials grant, third-party provider or wildcard scopes is selected. Authorization GET renders trusted login/consent UI; it never mints a code. The signed-in controller chooses a controlled instance and approves under bound step-up. Enrolled MFA applies normally.

Selected code/consent/access/refresh lifetimes are 60/300/600/86,400 seconds, within validated policy bounds. Backend must implement single-use codes, exact client/redirect/resource/PKCE binding, refresh rotation/reuse denial, audience verification and immediate live revocation. Token responses require no-store/no-cache. Invalid grants give generic OAuth errors; revocation gives a generic success without an existence oracle. Protected-resource discovery and `WWW-Authenticate` challenges must point to the actual deployed MCP resource. Validate Host/Origin, sizes and rates before dispatch.

References: [MCP revision](https://modelcontextprotocol.io/specification/2026-07-28), [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), [authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [official TypeScript SDK](https://github.com/modelcontextprotocol/typescript-sdk). The source specification and SDK schemas, rather than historical handshake examples, govern implementation.

## OpenAPI, Nest and Dart

`npm run generate` uses native Zod JSON Schema export to create OpenAPI **3.1.1**, the tool catalog and representative Dart sources. Export throws for unrepresentable schema constructs instead of weakening them to unchecked objects. Component-local references are rebased when embedded in OpenAPI. The exported artifact contains concrete transport representations, parameter requirements, response statuses, security schemes and policy extensions; production docs routes are absent. Development export is separately validated.

Future Nest adapters should validate input and outbound JSON with `apiRoutes`, perform shared service authorization/transactions, and give Swagger the generated document via `SwaggerModule.setup`. Do not infer independent class-validator DTOs or maintain a second field list. Optional controller metadata can point to existing component references. Swagger decorators, SDK hints, generated clients and JSON Schema validation cannot replace Zod custom refinements or live authorization. Metadata/export agreement is tested; no Nest runtime is implemented in this package.

The isolated `compat/dart` package derives RegisterRequest, UpdatePreferences, ArtifactMetadata, AuthResult (including nested session/user/MFA) and ApiError from OpenAPI components. Freezed and json_serializable generate the committed implementation/JSON files. Absent optional fields omit JSON members; explicit null fails; enums serialize their wire values; timestamps remain validated canonical UTC millisecond strings, preserving exact wire values. Auth challenges cannot deserialize as sessions. Generated validation metadata covers this bounded structural subset. Cross-field Zod refinements (for example, a nonempty preference patch), request normalization and live authority still run on the server; this is representative structural parity, not a full generated client or proof that JSON Schema encodes every domain rule.

`npm run check:generated` compares deterministic exports/source generation without rewriting files. `npm run verify:dart` uses `DART_BIN` (or `dart` on PATH), the pinned pub lock, Freezed regeneration and Dart formatting diff, analyzer and the shared fixture corpus. It fails if committed generator output changes. The pipeline normalizes generator-emitted trailing whitespace; Freezed disables ordinary formatting in its implementation file. `npm run generate:dart` intentionally regenerates these artifacts for review. It is a separate toolchain gate from Node verification, so a Node-only contributor must not claim Dart checks from `npm run verify` alone. No Flutter app is modified.

Pins: Node 24.21.0, TypeScript 5.9.3, Zod 4.6.6; MCP client/server 2.4.0; Swagger Parser 12.1.0; Ajv 8.20.0 / ajv-formats 3.0.1; Dart 3.13.4; Freezed 4.0.3 / annotation 3.1.0; json_serializable 6.15.2 / json_annotation 4.12.0; build_runner 2.17.1. Each package has its own lockfile; no root workspace or application dependencies are introduced.

## Compatibility and evidence

The package is private, version 1.0.0. This marks the first reviewable contract baseline. Future app owners request cross-app changes here first, identifying affected operations, consumers, authority/privacy effects, migrations and rollout order. Required/removed fields, tightened accepted inputs, changed enum variants, paths, statuses or authority/transport semantics require a major version or explicitly coordinated pre-release migration. Backward-compatible additions use a minor version only after strict-client compatibility is reviewed; documentation/generator fixes that preserve the wire shape use a patch. Strict responses mean even apparently additive fields/enums need consumer review. Never silently change an immutable evidence reference or reinterpret an old approval digest. Regenerate OpenAPI/Dart, run both gates, update this compatibility record and coordinate app-owner adoption before endpoint/client rollout.

Verification evidence is recorded in plan 00: 83 Node tests and 21 shared Dart fixtures, typecheck/dual builds, generated drift, OpenAPI validation, analyzer and Freezed regeneration all pass. It includes independent packed ESM/CommonJS consumers; every route inventory row and all feature/journey mappings; strict request/error projections; valid production/development OpenAPI; shared structural fixtures; signed cursor/digest tampering and scope checks; and official SDK client/server exchange through injected Fetch using synthetic authenticated contexts. Earlier existing lifecycle fixtures exercise register/login shapes through task/assignment/review/acceptance and cross-controller denial; they do not become real endpoints by joining this catalog.

The SDK check is real SDK-to-SDK serialization/transport interoperability, but in-process: it uses a fixture authentication boundary and shared pure policies. It does not prove deployed HTTP, production OAuth cryptography, PKCE redemption/refresh concurrency, independent operator runtimes, SQL prefilters, atomic receipts, actual event retention, provider scanning, erasure or client reconnect behavior. These remain backend E01–E16 and later app/security/release gates. Plan 00 can close at this interface baseline without checking any backend implementation box.
